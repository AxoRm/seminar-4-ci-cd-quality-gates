# Доклад для выступления (примерно 5–6 минут)

## Текст, который можно произнести

Мы спроектировали pipeline для backend интернет-магазина. Самый рискованный путь для пользователя — от входа и каталога до заказа, расчёта суммы, оплаты и истории заказов. Ошибка здесь может привести не только к неработающей странице, но и к неверному списанию или доступу к чужому заказу. Поэтому мы разделили проверки по скорости и по моменту, когда их результат действительно нужен.

Когда разработчик открывает MR или добавляет в него коммит, автоматически стартуют пять независимых jobs: линтер на 30 секунд, статический анализ на минуту, сборка на 2 минуты, 5000 unit-тестов на 3 минуты и проверка зависимостей на 2 минуты. При пяти доступных runner-слотах они идут параллельно. Время определяется самым длинным job, то есть 3 минуты. Мы оставляем ещё до 2 минут на очередь и подготовку окружения и получаем первые основные результаты примерно за 5 минут. Это укладывается в требование «не более 10 минут». Если runner-слотов меньше, это обещание уже не доказано, поэтому очередь надо измерять и для FAST зарезервировать ресурсы.

После сборки параллельно запускаются 700 integration-тестов на 15 минут и 300 API сценариев на 12 минут. Оба набора обязательны для merge, поэтому полный gate занимает ориентировочно 17 минут плюс сбор отчёта и служебные задержки. Важно не путать это время с требованием к первой обратной связи: в условии прямо разрешено, что полный pipeline длиннее. Мы не переносим все проверки за merge только ради красивой цифры. Integration проверяет реальные границы с БД и внешними сервисами, а API — контракт, статусы, авторизацию и негативные сценарии.

MR можно объединить только при нуле падений обязательных тестов, успешной сборке и анализе, отсутствии известных уязвимостей в зависимостях, выполнении порогов покрытия и code review. Для общего покрытия предлагаем минимум 80% строк и 70% ветвей; для новых строк — 85%; для модулей авторизации, цены, заказов и оплаты — 95% строк и 90% ветвей. Эти проценты не доказывают правильность программы сами по себе. Поэтому мы отдельно перечислили обязательные сценарии: округление суммы, границы скидок, конкуренция за остатки, повтор платежа, сбой платёжного провайдера и запрет просмотра чужих заказов. Пороги — наше проектное предложение. В настоящем проекте их сначала сравнивают с исходной базой и не снижают при новых изменениях.

После merge проверки повторяются на итоговом SHA ветки main: фактический результат объединения может отличаться от ветки MR. Затем один и тот же собранный артефакт автоматически разворачивается на TEST и на отдельный PERF. На TEST сначала проходит короткий smoke: вход, каталог, заказ, сумма, тестовая оплата и история. Потом идут все 150 E2E сценариев, на это отведено 50 минут. На PERF параллельно выполняется двухчасовая нагрузка. Стенды разделены, потому что нагрузочный тест на TEST исказил бы результаты E2E.

Release gate запрещает PROD, если E2E или нагрузка не прошли, smoke красный, есть серьёзный открытый дефект либо артефакт отличается от проверенного. Как пример численных порогов мы предлагаем менее 0,1% ответов 5xx и p95 менее 300 мс для каталога, 500 мс для заказа и 800 мс для тестового пути оплаты. Нулевая терпимость — к ошибке суммы и двойному платежу. Такие пороги имеют смысл только на репрезентативном стенде при заранее согласованном профиле нагрузки. PROD запускается вручную уполномоченным человеком после всех автоматических gates; сначала 5% трафика, затем контроль метрик и полный rollout. При ухудшении — остановка и откат.

Когда тестовая база вырастет, unit займут 5 минут, integration — 25, API — 20, E2E — 70. Быстрый контур всё ещё будет давать ответ за 5 минут работы плюс до 2 минут служебного времени, то есть не позднее 7 минут при наших условиях. Полный MR gate станет примерно 27 минут плюс агрегация. Чтобы ускорить его без потери защиты, можно разделить integration на пять независимых частей, API — на четыре, обеспечить изолированные данные и объединить отчёты. При идеальном балансе каждая часть займёт около 5 минут плюс запуск. Риск — тесты начнут влиять друг на друга через общую базу или разное состояние окружения, поэтому каждый shard должен иметь изоляцию. Выборочный запуск полезен для раннего сигнала, но полный набор остаётся обязательным до merge.

Отдельно мы прописали политику flaky-тестов. Если тест прошёл со второго раза, мы не считаем первый провал несуществующим. Retry допускается для диагностики сбоя инфраструктуры с сохранением логов. Критические тесты денег и доступа не отправляются в карантин. Некритический нестабильный тест получает владельца, задачу и срок исправления; в nightly он продолжает запускаться. Так pipeline остаётся быстрым, но зелёный статус по-прежнему что-то означает.

## Если преподаватель спросит

**Почему не запускаете E2E в каждом MR?** Полный набор занимает 50 минут, часто зависит от стенда. Merge уже защищён unit, integration и API; E2E обязательно закрывает выпуск в PROD. Для особо опасных изменений в оплате можно запускать целевой E2E раньше дополнительно.

**Почему 6 минут из условия не совпадают с вашим расчётом?** Шесть минут — текущее среднее время существующего pipeline. После добавления полных обязательных проверок его длительность изменится. Мы отдельно считаем быстрый отклик и полное ожидание merge.

**Почему покрытие 80%, а не 100%?** Процент помогает обнаружить непроверенный код, но не оценивает качество assertions. 100% может включать бессмысленные тесты. Для денежных и правовых инвариантов порог выше, а обязательные негативные сценарии задаются по риску.

**Что будет, если один из 700 тестов иногда падает?** MR остаётся красным, пока причина не установлена. Повтор для диагностики разрешён, автоматическое превращение красного в зелёный — нет. Критический flaky-тест исправляется, а некритический можно кратковременно изолировать с явным сроком.

**Чем доказывается укладывание в 10 минут?** Параллельным расписанием: максимум среди пяти FAST jobs — 3 минуты сейчас и 5 минут в прогнозе. Резерв на очередь и запуск — 2 минуты. Это требует достаточного числа runner-слотов и мониторинга фактического p95, иначе расчёт остаётся предположением.
